## 1. Цели и область применения

**Цель:** создать веб-мессенджер для безопасного общения в реальном времени без установки отдельного приложения.

**Продукт (MVP):** веб-сервис для пользователей, которым нужна быстрая и приватная текстовая переписка.

**Входит в проект:** клиентская и серверная части, проектирование БД, регистрация и авторизация, обмен сообщениями в реальном времени, хранение истории, базовая защита данных, тестирование, развёртывание.

**Не входит в MVP:** групповые чаты, звонки, сквозное шифрование (E2EE), мобильные приложения.

## 3. Архитектура

Система разделена на четыре слоя: клиент, edge/proxy, бизнес-логика, хранение данных.

```mermaid
flowchart LR
    subgraph L1 [1. Client Layer]
        direction TB
        React[React + TS Web]
        RxDB[(RxDB / IndexedDB)]
        React <-->|Чтение/Запись| RxDB
    end

    subgraph L2 [2. Edge / Proxy Layer]
        direction TB
        Nginx[Nginx Reverse Proxy]
    end

    subgraph L3 [3. Business Logic Layer]
        direction TB
        SignalR[SignalR Hub - WSS]
        REST[REST API - HTTP]
    end

    subgraph L4 [4. Data & Storage Layer]
        direction TB
        Redis[(Redis - Backplane)]
        Postgres[(PostgreSQL - ULID)]
        S3[(S3 - Media Storage)]
    end

    React ==>|WSS Сообщения| Nginx
    React ==>|HTTP История/Медиа| Nginx
    React -.->|Прямой PUT файла| S3

    Nginx ==>|Upgrade to WSS| SignalR
    Nginx ==>|Reverse Proxy HTTP| REST

    SignalR <-->|Pub/Sub & Статусы| Redis
    SignalR ==>|INSERT Dapper| Postgres
    REST <-->|EF Core / Dapper| Postgres
    REST -.->|Генерация Presigned URL| S3
```

**WSS** — WebSocket Secure (WebSocket поверх TLS).

### Принятые архитектурные решения

| Решение | Обоснование |
|---------|-------------|
| Offline-First (RxDB) | Мгновенный отклик интерфейса, работа при нестабильной сети |
| SignalR + Redis backplane | Рассылка событий между несколькими инстансами бэкенда |
| ULID вместо UUID/serial | Сортируемые по времени ключи — вставка в конец индекса, меньше фрагментации |
| EF Core + Dapper (CQRS-подход) | EF — для редких операций, Dapper — для высокочастотной вставки сообщений |
| Pre-signed URL для медиа | Файлы идут напрямую в S3, бэкенд не нагружается |
| Redis для presence | Статусы «онлайн»/«печатает» не нагружают PostgreSQL |

## 4. Клиентский слой

**Стек:** React, TypeScript, RxDB (IndexedDB).

- **Optimistic UI.** При отправке сообщение сразу записывается в локальную БД и отображается. Подтверждение от сервера обновляет его статус.
- **Реальное время.** Постоянное WSS-соединение с SignalR Hub.
- **Синхронизация после офлайна.** Клиент делает HTTP-запрос дельты, передавая `LastSyncULID` — ULID последнего известного сообщения. Сервер возвращает всё более новое.
- **Медиа.** Клиент запрашивает у REST API короткоживущий Pre-signed URL и отправляет файл напрямую в S3 методом PUT.
- **Сохранение состояния** при обновлении страницы: токен сессии, открытый диалог и позиция прокрутки.

## 5. Слой маршрутизации и бизнес-логики

**Стек:** Nginx, C# .NET 10, SignalR, REST API.

### Nginx

Единая точка входа: терминирует HTTPS, проксирует обычные запросы на REST API, а запросы с `Upgrade: websocket` — на SignalR.

### Общие правила API

- Все эндпоинты, кроме `register` и `login`, требуют заголовок `Authorization: Bearer <accessToken>`.
- Идентификаторы (`id`, `userId`, `dialogId`) — ULID, строка из 26 символов. Порядок сортировки ULID совпадает с хронологическим.
- Ошибки возвращаются в формате `application/problem+json` (RFC 7807): `400` — невалидные данные, `401` — нет или неверный токен, `404` — не найдено или нет доступа, `409` — конфликт, `429` — превышен лимит запросов.
- Для чужих диалогов возвращается `404`, а не `403`, чтобы не раскрывать их существование.
- Логин и email хранятся в нижнем регистре.

### REST API

| Метод | Путь | Назначение | Ответ |
|-------|------|------------|-------|
| POST | `/api/auth/register` | Регистрация | `200` `{accessToken, expiresAt, user}`; `409` если логин или email занят |
| POST | `/api/auth/login` | Вход по логину или email | `200` `{accessToken, expiresAt, user}`; `401` при неверных данных |
| POST | `/api/auth/refresh` | Новый access-токен по httpOnly-cookie (ротация refresh-токена) | `200` `{accessToken, expiresAt, user}`; `401` |
| POST | `/api/auth/logout` | Выход: отзыв refresh-токена, очистка cookie | `204` |
| POST | `/api/auth/password` | Смена пароля `{currentPassword, newPassword}`; остальные сессии отзываются | `204`; `400` неверный текущий |
| GET | `/api/users/me` | Свой профиль | `200` `profile` |
| PUT | `/api/users/me` | Изменить `displayName`, `avatarUrl` (публичный https), `bio` (до 300; `null` — не менять, `""` — очистить) | `200` `profile` |
| GET | `/api/users/{id}` | Профиль человека; онлайн/«был(а) в сети» — только для собеседников | `200` `profile`; `404` |
| GET | `/api/users/search?q=&scope=` | **Поиск людей** по словам в логине и имени (любой порядок, `@` игнорируется); `scope=all\|contacts` | `200` `user[]` |
| GET | `/api/users?query=` | Список «Люди»: без `query` — все по алфавиту, с `query` — поиск как выше; `limit`, `offset` | `200` `user[]` |
| GET | `/api/messages/search?q=` | **Поиск сообщений** по словам (все должны встретиться), `dialogId`, `before`, `limit` | `200` `message[]` |
| PUT | `/api/messages/{id}` | Изменить текст своего сообщения | `200` `message` |
| GET | `/api/dialogs/{id}/pins` | Закреплённые сообщения | `200` `message[]` |
| PUT/DELETE | `/api/dialogs/{id}/pins/{messageId}` | Закрепить / открепить (до 10 на диалог) | `204`; `409` лимит |
| POST | `/api/dialogs/{id}/forward` | Переслать до 50 сообщений `{toDialogId, messageIds, clientBatchId}` в другой свой диалог | `200` `message[]` |
| GET | `/api/dialogs` | Список диалогов с собеседником и последним сообщением | `200` `dialog[]` |
| POST | `/api/dialogs` | Создать диалог `{userId}`; если уже есть — вернуть существующий | `201` новый, `200` существующий |
| DELETE | `/api/dialogs/{id}` | Удалить диалог целиком (у обоих участников) | `204` |
| GET | `/api/dialogs/{id}/messages` | История и дельта (параметры ниже) | `200` `message[]` по возрастанию ULID |
| DELETE | `/api/messages/{id}?scope=all\|me` | Удалить у обоих (мягкое удаление, снимает закреп) или скрыть только у себя | `204`; `404` |
| POST | `/api/media/upload-url` | Получить Pre-signed URL | не реализовано |

Параметры истории сообщений:

| Параметр | Назначение |
|----------|------------|
| `after={ULID}` | Только более новые сообщения — дельта-синхронизация (`LastSyncULID`) |
| `before={ULID}` | Только более старые сообщения — подгрузка истории вверх |
| `limit` | Размер страницы, 1–100, по умолчанию 50 |

`after` и `before` нельзя указывать одновременно. Без них возвращаются последние `limit` сообщений. Удалённые сообщения в выдачу не попадают.

Формат объектов:

```
user    { id, login, displayName, avatarUrl }
profile { id, login, displayName, avatarUrl, bio, createdAt, isOnline?, lastSeenAt? }
message { id, clientMessageId, dialogId, senderId, text, mediaUrl, createdAt, editedAt,
          replyToId, forwardedFromId, forwardedFromName }
dialog  { id, createdAt, peer: user, lastMessage: message | null, unreadCount, peerLastReadId }
```

### SignalR Hub

Адрес: `/hubs/chat`. Токен передаётся в query-параметре `access_token` (для WebSocket) или в заголовке `Authorization`.

| Направление | Событие | Описание |
|-------------|---------|----------|
| клиент → сервер | `SendMessage(clientMessageId, dialogId, text)` | Отправка сообщения. Возвращает серверный ULID. Лимиты: `clientMessageId` до 64 символов, `text` 1–4000 символов |
| сервер → клиент | `MessageReceived(message)` | Новое сообщение. Приходит всем участникам диалога, включая другие устройства отправителя |
| сервер → клиент | `MessageAcked(clientMessageId, serverUlid)` | Подтверждение сохранения, только отправившему соединению |
| сервер → клиент | `MessageDeleted(dialogId, messageId)` | Сообщение удалено |
| клиент → сервер | `SendReply(clientMessageId, dialogId, text, replyToId)` | Ответ на сообщение того же диалога; ошибка `invalid_reply_to`, если цель чужая или удалена |
| сервер → клиент | `MessageEdited(message)` | Текст изменён |
| сервер → клиент | `MessagePinned(dialogId, message, pinnedById)` / `MessageUnpinned(dialogId, messageId)` | Закреп изменился |
| клиент → сервер | `Typing(dialogId)` | Статус «печатает» |
| сервер → клиент | `UserTyping(dialogId, userId)` | Собеседник печатает |
| сервер → клиент | `PresenceChanged(userId, status)` | `online` / `offline` для тех, с кем есть диалоги |

Ошибки хаба приходят клиенту как `HubException` с кодом в сообщении: `forbidden` (не участник диалога), `invalid_text`, `invalid_client_message_id`, `invalid_reply_to`, `rate_limited`, `unauthorized`.

Соединение закрывается сервером, когда истекает access-токен, с которым оно открыто; клиент переподключается со свежим токеном.

Клиент должен отсеивать собственные сообщения в `MessageReceived` по `clientMessageId`, поскольку событие приходит и отправителю.

### Идемпотентность

Каждое сообщение несёт уникальный клиентский ключ (`clientMessageId`). Если соединение моргнуло и клиент повторил отправку, сервер находит уже сохранённое сообщение с этим ключом и не создаёт дубликат. При повторе клиент получает тот же `serverUlid` и `MessageAcked`, но `MessageReceived` участникам повторно не рассылается.

### Доступ к данным (CQRS-подход)

- **EF Core** — редкие операции (профиль, смена имени, диалоги).
- **Dapper** — сверхчастая вставка сообщений и чтение истории, прямые SQL без лишних аллокаций.

## 6. Слой хранения данных

### PostgreSQL

Основное хранилище. Для таблицы сообщений используется **партиционирование** (например, по диапазону времени/ULID) и **ULID** в качестве ключа.

Предварительная модель данных (уточняется программистом БД):

```
users        (id ULID PK, login, email, password_hash, display_name, avatar_url, bio, created_at, last_seen_at)
dialogs      (id ULID PK, created_at)
dialog_members (dialog_id FK, user_id FK, joined_at, PRIMARY KEY (dialog_id, user_id))
messages     (id ULID PK, client_message_id, dialog_id FK, sender_id FK,
              text, media_url NULL, created_at, edited_at NULL, deleted_at NULL,
              reply_to_id NULL FK→messages (ON DELETE SET NULL),
              forwarded_from_id NULL, forwarded_from_name NULL,
              UNIQUE (sender_id, client_message_id))
pinned_messages (dialog_id FK, message_id FK, pinned_by_id, pinned_at, PRIMARY KEY (dialog_id, message_id))
message_hides   (message_id FK, user_id FK, created_at)   -- «удалить у меня»
```

Особенности реализации:

- ULID хранится в колонке `varchar(26)` с коллацией `"C"`. Без побайтового сравнения порядок сортировки не совпадёт с хронологическим.
- `created_at` сообщения проставляет БД (`now()`), чтобы часы были единые для всех инстансов бэкенда.
- Уникальный индекс `(sender_id, client_message_id)` обеспечивает идемпотентность на уровне БД. При партиционировании `messages` его нужно расширить ключом партиции.
- Индекс `(dialog_id, id)` обслуживает историю и дельта-синхронизацию.
- Поиск по частям (`ILIKE '%слово%'`) ускоряют триграммные GIN-индексы (расширение `pg_trgm`) на `messages.text`, `users.login`, `users.display_name`.
- Удаление диалога каскадно удаляет участников и сообщения; удаление сообщения — мягкое (`deleted_at`).

Резервное копирование — регулярные дампы (`pg_dump`) или WAL-архивация; периодически проверять восстановление.

### Redis

- **Backplane** SignalR — трансляция событий между инстансами сервера.
- **Presence** — эфемерные статусы «онлайн» и «печатает» с TTL (см. раздел 14: пока в памяти процесса).

### S3

Хранилище изображений и видео. Бэкенд только выдаёт Pre-signed URL; доступ к объектам ограничен.

## 7. Ключевые сценарии

### Отправка сообщения

1. Пользователь нажимает «Отправить».
2. Клиент записывает сообщение в RxDB со статусом `pending` — UI обновляется сразу.
3. Клиент отправляет `SendMessage` по WSS.
4. Hub проверяет, что пользователь состоит в диалоге, и проверяет идемпотентность.
5. Сообщение вставляется в PostgreSQL (Dapper).
6. Событие публикуется через Redis backplane всем участникам диалога.
7. Отправитель получает `MessageAcked`, статус меняется на `sent`.

### Возвращение из офлайна

1. Клиент восстанавливает WSS-соединение.
2. Запрашивает `GET /api/dialogs/{id}/messages?after={LastSyncULID}`.
3. Объединяет полученные сообщения с локальной БД.
4. Отправляет повторно все сообщения со статусом `pending` (идемпотентность защищает от дублей).

Ограничение: удаления старых сообщений в дельту не попадают, поскольку выдача идёт по ULID. Клиент получает их через событие `MessageDeleted` или при полной перезагрузке истории.

### Загрузка медиа

1. Клиент запрашивает `POST /api/media/upload-url`.
2. Бэкенд генерирует Pre-signed URL с коротким сроком жизни.
3. Клиент загружает файл напрямую в S3.
4. В сообщении сохраняется ссылка на объект.

## 8. Безопасность и шифрование

### Что реализуется в MVP

| Мера | Описание |
|------|----------|
| TLS (HTTPS/WSS) | Шифрование трафика между клиентом и сервером на уровне Nginx |
| Хеширование паролей | bcrypt (work factor 11); пароли в открытом виде не хранятся и не логируются. Пароль до 72 символов |
| Аутентификация | JWT access-токен (15 минут) + refresh-токен в httpOnly-cookie с ротацией и обнаружением повторного предъявления; смена пароля отзывает остальные сессии. SignalR-соединение закрывается по истечении токена |
| Авторизация | Проверка членства в диалоге при каждом чтении/записи сообщений |
| Валидация ввода | На сервере; экранирование вывода на клиенте (защита от XSS) |
| Защита от SQL-инъекций | Параметризованные запросы (EF Core, Dapper) |
| Ограничение частоты | Авторизация — 10 запросов в минуту с IP; остальной REST — 60 в минуту на пользователя (`RateLimiting:UsersPerMinute`); хаб — по методам. Перебор пароля: 10 неудач на пару «IP + логин» и 50 на аккаунт за 15 минут |
| CORS и заголовки | Строгая политика CORS (список origin в конфигурации); CSP и HSTS — на уровне Nginx |
| Шифрование хранилищ | Шифрование диска/БД и server-side encryption в S3 |
| Секреты | Только через переменные окружения / секретницу, не в репозитории |
| Логи | Тексты сообщений и токены в логи не пишутся |

### Сквозное шифрование (E2EE)

В MVP **не реализуется.** Причины: усложняет серверный поиск и синхронизацию дельты, требует управления ключами и поддержки нескольких устройств (протокол уровня Signal), а срок проекта и размер команды ограничены. Сервер может читать содержимое сообщений, поэтому защита строится на разграничении доступа и защите инфраструктуры.

Допустимый компромисс — шифрование текста сообщения в БД на уровне приложения (AES-GCM, ключ вне БД). Решение принимается командой отдельно.

## 9. Тестирование

|---------|---------------|-------------|
| Unit | Бизнес-логика, валидация, выдача токена | xUnit |

| SignalR | Отправка/получение событий, права доступа | Microsoft.AspNetCore.SignalR.Client |

### Frontend (`frontend/`)

| Уровень | Что проверяем | Инструменты |
|---------|---------------|-------------|
| Unit | Утилиты, хуки, логика синхронизации | Vitest / Jest |
| Компонентные | Рендер и поведение компонентов | React Testing Library |
| E2E | Регистрация → поиск → диалог → сообщение | Playwright / Cypress |

### Ключевые тест-кейсы

- Регистрация и вход, невалидные данные
- Недоступность чужого диалога (проверка авторизации)
- Доставка сообщения между двумя пользователями в реальном времени

## Клиент: действия с сообщениями, поиск и профиль

- **Меню сообщения** открывается правой кнопкой мыши, долгим нажатием (500 мс) или кнопкой «⋯»; управление стрелками и Esc. Пункты: «Ответить», «Копировать» (при выделении текста — «Копировать выделенное»), «Изменить» (только своё), «Закрепить/Открепить», «Переслать…», «Удалить». Ответ, закреп и пересылка доступны только для уже отправленных сообщений (у них есть серверный id).
- **Ответ** уходит методом хаба `SendReply`; если исходное сообщение к моменту отправки удалено, текст отправляется как обычное сообщение. Цитата в пузыре ведёт к оригиналу.
- **Закреп** общий для диалога: строка над перепиской, клик прокручивает к сообщению и переключает на следующее закреплённое. Список берётся с сервера (`GET /pins`) и обновляется событиями `MessagePinned`/`MessageUnpinned`.
- **Пересылка** работает только онлайн (`POST /forward`); метка «Переслано от …» показывается над текстом.
- **Разделы (боковая панель):** «Чаты», «Люди», «Настройки». На телефоне та же панель внизу; при открытом диалоге она скрыта.
- **Поиск разделён по местам:** в «Чатах» — по имени или логину собеседника (локально); в «Людях» — по всем пользователям (`/api/users/search`, по 30 за раз, «Показать ещё»); по тексту — внутри самого чата (лупа в шапке, `/api/messages/search?dialogId=`, по 30 за раз). Найденное сообщение подсвечивается; если оно старше загруженной истории, история подгружается страницами вверх. Слова ищутся в любом порядке.
- **Профиль:** клик по имени в шапке диалога или по человеку в «Людях» открывает профиль («о себе», статус, дата регистрации; в «Людях» — кнопка «Написать»).
- **Настройки сгруппированы:** Аккаунт (профиль, безопасность), Приложение (внешний вид, уведомления), Устройство (сессия и кэш). «Внешний вид»: тема авто/светлая/тёмная и акцентный цвет (хранятся в `localStorage`, `lib/theme.ts`). Вкладки «Синхронизация» нет: синхронизация автоматическая.
- **Статус «в сети»:** зелёная точка на аватаре (у тех, кто не в сети, точки нет) и зелёная подпись «в сети» в шапке диалога и профиле.
- **Порционная загрузка:** история диалога — по 50 сообщений (вверх по прокрутке), дельта-синхронизация — по 100; люди и результаты поиска — по 30; список диалогов загружается целиком.
- Локальная БД теперь `messenger4-…` (добавлены `replyToId`, `fwdFrom`); данные восстанавливаются с сервера при первом запуске.

## Файловое хранилище (S3)

Файлы (аватарки, обои, голосовые, фото) хранятся не в БД и не на диске сервера (на Render диск эфемерный), а в S3-совместимом хранилище. Код работает через интерфейс `IFileStorage` (`Storage/`): `PutAsync`, `GetAsync`, `DeleteAsync`, `GetDownloadUrl` (временная ссылка). Реализация `S3FileStorage` одинакова для всех провайдеров, различаются только переменные окружения.

| Переменная | Локально (MinIO) | Прод (Yandex Object Storage) |
|---|---|---|
| `Storage__Endpoint` | `http://localhost:9000` | `https://storage.yandexcloud.net` |
| `Storage__Region` | `us-east-1` | `ru-central1` |
| `Storage__Bucket` | `messenger` | имя бакета |
| `Storage__AccessKey` / `Storage__SecretKey` | `messenger` / `messenger_dev_password` | статический ключ сервисного аккаунта |
| `Storage__ForcePathStyle` | `true` | `false` |
| `Storage__EnsureBucket` | `true` (бакет создаётся сам) | `false` |

- **Без настроек** приложение стартует с заглушкой `DisabledFileStorage`: файловые функции отвечают 503, остальное работает (удобно для тестов и быстрого запуска без MinIO).
- **При старте** (если хранилище настроено) в лог пишется «Storage is ready» либо предупреждение с причиной; ошибка хранилища не останавливает приложение.
- **Настройка Yandex Cloud:** 1) создать бакет (доступ «ограниченный»); 2) создать сервисный аккаунт с ролью `storage.editor` на каталог или бакет; 3) выпустить ему статический ключ доступа (идентификатор и секрет показываются один раз); 4) задать переменные в Environment сервиса на Render. Ключи не коммитятся.
- **Ключи объектов:** `avatars/{userId}/{ulid}.webp`, `wallpapers/{userId}/{ulid}.webp`, `media/{dialogId}/{ulid}.{ext}`, `voice/{dialogId}/{ulid}.ogg`.
- **Проверка против настоящего бакета:** интеграционный тест `Live_roundtrip_against_a_real_bucket_when_configured` выполняется, только если заданы `STORAGE_TEST_BUCKET`, `STORAGE_TEST_ACCESS_KEY`, `STORAGE_TEST_SECRET_KEY` (и при необходимости `STORAGE_TEST_ENDPOINT`, `STORAGE_TEST_REGION`, `STORAGE_TEST_PATH_STYLE=true`).
- Если Yandex отвечает ошибкой подписи при загрузке, первым делом проверьте регион (`ru-central1`) и endpoint; контрольные суммы SDK по умолчанию отключены (`WHEN_REQUIRED`), так как не все S3-совместимые хранилища их понимают.

## Загрузка аватарок и обои

- **Обработка** (`Media/ImageProcessor.cs`, SkiaSharp): реальное декодирование, лимит 36 Мпикс (защита от «бомб»), поворот по EXIF, перекодирование в WebP — так в хранилище попадают только безопасные картинки без метаданных.
- **Ключи:** `avatars/{userId}/{ulid}.webp` (публичные, неизменяемые, кэш на год) и `wallpapers/{userId}/{ulid}.webp` (приватные, путь строится от текущего пользователя). При смене аватарки прежний файл удаляется.
- **Оформление** (`users.appearance`, jsonb): тема, акцентный цвет, обои (пресет или загруженное фото + затемнение), форма пузырей, плотность, шрифт и размер текста. Клиент держит копию в `localStorage` и синхронизирует с сервером (`lib/theme.ts`), поэтому вид одинаков на всех устройствах. Пресеты обоев — CSS без файлов.
- **Дальше по той же схеме:** фото и голосовые сообщения (`media/`, `voice/`) — приватные файлы с проверкой членства в диалоге.
